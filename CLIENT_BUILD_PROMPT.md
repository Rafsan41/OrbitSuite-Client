# Backend API contract

Base URL: `http://localhost:5000/api/v1` (put it in `NEXT_PUBLIC_API_URL`).

## Response envelope — every endpoint, success and failure

```jsonc
// success
{ "success": true, "message": "Plans retrieved", "data": {}, "meta": { "page": 1, "limit": 20, "total": 42, "totalPages": 3 } }

// failure
{ "success": false, "message": "You do not have permission to perform this action", "data": null }

// validation failure adds field-level detail
{ "success": false, "message": "Validation failed", "data": null,
  "errors": [ { "field": "email", "message": "A valid email is required" } ] }
```

`meta` appears only on paginated list endpoints. `errors` only on 400 validation
failures — surface these inline on the matching form field.

## Authentication

- `POST /auth/login` returns `data.accessToken` (JWT, **15-minute** lifetime) and
  sets an **httpOnly refresh cookie** (7 days).
- Send the access token as `Authorization: Bearer <token>`.
- **Axios must set `withCredentials: true`** or the refresh cookie is never sent.
  Backend CORS uses `credentials: true` against `CLIENT_URL=http://localhost:3000`.
- On a 401, call `POST /auth/refresh` once (no body — it reads the cookie), retry
  the original request with the new token, and if the refresh also fails, clear
  the session and redirect to `/login`. Guard against infinite retry loops and
  make concurrent 401s share a single refresh.
- Keep the access token **in memory** (React state or a query cache entry). Do
  not put it in `localStorage`.
- `POST /auth/logout` clears the cookie.

`GET /auth/me` returns the current user, their organization and its subscription
— use it to hydrate the session on load.

## Roles

`PLATFORM_ADMIN` · `ORG_ADMIN` · `ORG_MEMBER`

Access is enforced server-side; your job is to avoid showing users doors they
cannot open. A 403 must still render a clean "no access" state, not a crash.

## Organization statuses

`PENDING` (registered, not yet paid) · `ACTIVE` · `TRIAL` · `SUSPENDED` · `CANCELLED`

**A `PENDING` organization must be routed to checkout**, not into the app. A
`SUSPENDED` organization is refused at login by the backend — show the message.

## Endpoints

### Auth
| Method | Path | Roles | Body |
|---|---|---|---|
| POST | `/auth/register` | public | `{ organizationName, name, email, password, planId }` |
| POST | `/auth/login` | public | `{ email, password }` |
| POST | `/auth/refresh` | cookie | — |
| POST | `/auth/logout` | public | — |
| POST | `/auth/forgot-password` | public | `{ email }` |
| POST | `/auth/reset-password` | public | `{ token, password }` |
| GET | `/auth/me` | any | — |
| POST | `/auth/change-password` | any | `{ currentPassword, newPassword }` |

Password rules (mirror in zod): min 8, max 72, at least one lowercase, one
uppercase, one number.

### Plans
| Method | Path | Roles |
|---|---|---|
| GET | `/plans?page&limit&includeInactive` | **public** |
| GET | `/plans/:id` | public |
| POST | `/plans` | PLATFORM_ADMIN — `{ name, priceCents, billingInterval: "MONTH"\|"YEAR", features: string[] }` |
| PATCH | `/plans/:id` | PLATFORM_ADMIN — `{ name?, features?, isActive? }` |
| PATCH | `/plans/:id/disable` · `/plans/:id/enable` | PLATFORM_ADMIN |

**Price and billing interval are not editable** — Stripe prices are immutable.
The edit form must not offer them; say so in the UI ("Create a new plan to change
pricing").

### Organizations
| Method | Path | Roles |
|---|---|---|
| GET | `/organizations?page&limit&search&status&planId` | PLATFORM_ADMIN |
| GET | `/organizations/:id` | PLATFORM_ADMIN — detail incl. members, payments, transactions |
| PATCH | `/organizations/:id/suspend` · `/reactivate` | PLATFORM_ADMIN |
| GET | `/organizations/me` | ORG_ADMIN |
| PATCH | `/organizations/me` | ORG_ADMIN — `{ name?, contactEmail?, billingEmail? }` |
| GET | `/organizations/me/summary` | ORG_ADMIN, ORG_MEMBER — reduced, no financials |

List rows return `id, name, contactEmail, status, createdAt, memberCount, plan,
subscriptionStatus`.

### Users / members
| Method | Path | Roles |
|---|---|---|
| GET | `/users?page&limit&search&role&status` | ORG_ADMIN |
| POST | `/users/invite` | ORG_ADMIN — `{ name, email, role: "ORG_ADMIN"\|"ORG_MEMBER" }` |
| POST | `/users/accept-invite` | **public** — `{ token, password }` |
| GET | `/users/me` · PATCH `/users/me` | any — `{ name?, email? }` |
| PATCH | `/users/:id/role` | ORG_ADMIN — `{ role }` |
| DELETE | `/users/:id` | ORG_ADMIN — soft delete |

The invite token is emailed, never returned in the response. The accept-invite
page reads it from `?token=` in the URL.

Removing yourself, removing the last admin, or demoting the last admin all return
**409** — surface the message, do not treat it as a crash.

### Checkout
| Method | Path | Roles |
|---|---|---|
| POST | `/checkout/session` | ORG_ADMIN — returns `{ checkoutUrl, sessionId, plan }` |
| GET | `/checkout/status` | ORG_ADMIN — returns `{ subscriptionStatus, organizationStatus, plan, canRetry }` |

Redirect the browser to `checkoutUrl`. Stripe returns to
`/checkout/success?session_id=...` or `/checkout/cancel`.

**Critical:** the success page must **not** treat the redirect as proof of
payment — a redirect can be forged. Payment is confirmed only by a Stripe webhook
reaching the backend. The success page should poll `GET /checkout/status` (every
2s, ~30s cap) until `organizationStatus` is `ACTIVE`, showing "confirming your
payment…", then route into the app; if it never confirms, offer a retry. Put this
reasoning in a code comment — it is a graded design point.

### Subscriptions
| Method | Path | Roles |
|---|---|---|
| GET | `/subscriptions/me` | ORG_ADMIN, ORG_MEMBER — incl. `daysUntilRenewal`, `isExpired` |
| POST | `/subscriptions/change-plan` | ORG_ADMIN — `{ planId }` |
| POST | `/subscriptions/cancel` | ORG_ADMIN — `{ reason? }` |
| POST | `/subscriptions/expire` | PLATFORM_ADMIN — expiry sweep |
| GET | `/subscriptions/expiring-soon` | PLATFORM_ADMIN |
| POST | `/subscriptions/notify-expiring` | PLATFORM_ADMIN |

Cancel returns either `{ status: "cancellation_requested" }` (Stripe confirms by
webhook — tell the user it is pending) or `{ status: "cancelled" }`. Handle both
messages distinctly.

### Payments / transactions / stats
| Method | Path | Roles |
|---|---|---|
| GET | `/payments?page&limit&status` | ORG_ADMIN |
| GET | `/payments/:id` | ORG_ADMIN — invoice-shaped, incl. `invoiceNumber` |
| GET | `/transactions?page&limit&status&type&from&to` | ORG_ADMIN — own org |
| GET | `/transactions/all?...&organizationId` | PLATFORM_ADMIN — every tenant |
| GET | `/stats` | PLATFORM_ADMIN |

Transaction statuses: `PENDING` `SUCCESS` `FAILED` `REFUNDED` `ROLLED_BACK`.
Payment statuses: `PENDING` `SUCCESS` `FAILED` `REFUNDED`.

`/stats` returns:
```jsonc
{ "organizations": { "total": 4, "byStatus": { "ACTIVE": 4 }, "recentSignups": [] },
  "users": { "total": 7 },
  "subscriptions": { "active": 3, "byPlan": [ { "planName": "Starter", "subscribers": 2, "monthlyRecurringCents": 5800 } ] },
  "revenue": { "totalCents": 22700, "successfulPayments": 3, "failedPayments": 0 } }
```

All money is in **cents** — format for display, never render raw integers.

### Rate limits
Login/register: 15-minute window. Forgot/reset password: 1-hour window. On 429
show the returned message rather than a generic error.

# Pages to build

## Public
- `/` — landing. Product name, one line of copy, plan cards from `GET /plans`,
  links to login and register. Keep it to one screen.
- `/login`
- `/register` — organization name, admin name, email, password, plan selection.
  On success the org is `PENDING`; immediately create a checkout session and
  redirect to Stripe.
- `/forgot-password`, `/reset-password?token=`
- `/accept-invite?token=` — set a password, then route to login.
- `/checkout/success?session_id=`, `/checkout/cancel`

## Platform Admin — `/admin`
- `/admin` — stats overview: total orgs, total users, active subscriptions, total
  revenue, failed payments, recent signups, subscribers per plan.
- `/admin/organizations` — table with search + status filter; columns name, plan,
  status, members, signup date; row click → detail.
- `/admin/organizations/[id]` — profile, members, subscription, payments,
  transactions; suspend / reactivate actions.
- `/admin/plans` — table, create dialog, edit dialog, enable/disable toggle.
- `/admin/transactions` — platform-wide table, filters for org / status / date.

## Org Admin — `/org`
- `/org` — organization profile, view and edit.
- `/org/members` — table with role and status; invite dialog; change-role; remove.
- `/org/subscription` — current plan, renewal date, status; upgrade/downgrade via
  plan picker; cancel with a confirmation dialog.
- `/org/billing` — payment history table; row → invoice detail view.
- `/org/transactions` — own-org table with status filter.

## Member — `/me`
- `/me` — own profile, edit name/email, change password.
- `/me/organization` — read-only org name, plan, member count. Nothing financial.

# Implementation requirements

## Build these shared pieces first — they are what makes the page count feasible

1. **`components/data-table.tsx`** — one generic table taking columns, rows,
   `meta`, loading/error/empty states and pagination controls. **All eight table
   pages use this.** Do not write a second table.
2. **`components/states.tsx`** — `<LoadingState />`, `<ErrorState />`,
   `<EmptyState />` and a skeleton row. Used by the table and by detail pages.
3. **`components/status-badge.tsx`** — one badge mapping every status enum (org,
   subscription, payment, transaction, user) to a colour. Legible, not decorative.
4. **`lib/api-client.ts`** — axios instance, `withCredentials: true`, bearer
   interceptor, single-flight refresh-on-401, and a helper that unwraps the
   `{ success, message, data }` envelope and throws a typed `ApiError` carrying
   `message` and `errors[]`.
5. **`lib/format.ts`** — `formatMoney(cents)`, `formatDate`, `formatRelative`.
6. **`hooks/use-auth.ts`** — session from `/auth/me`, login, logout, role helpers.

## Routing and guards

- Route groups: `app/(auth)`, `app/(platform)`, `app/(org)`, `app/(member)`.
- A layout per group checks role and redirects: wrong role → their own home; no
  session → `/login`; `PENDING` org → checkout retry.
- Guards are **convenience, not security** — the server enforces access. Add a
  comment saying so; a reviewer will probe this.

## Forms

- react-hook-form + zod resolvers, schemas mirroring the backend's.
- On a 400, map `errors[].field` onto the matching input.
- Disable submit while pending, show a spinner, toast on success and failure.

## Quality bar

- Responsive: tables scroll horizontally on mobile, sidebar collapses.
- Every mutation invalidates the right TanStack Query keys.
- No `any`, no unused imports. `npm run build` and `npm run lint` pass clean.
- Semantic HTML, labelled inputs, keyboard-usable dialogs.
